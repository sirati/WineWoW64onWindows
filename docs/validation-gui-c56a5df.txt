Guest user32 and gdi32 use Wine's own win32u, compiled with its null display
driver into the x64 host, through the original wow64win thunks. The window,
message queue, hook, class, atom, winstation, user handle, region and
clipboard state is Wine's server code, run in-process. The host's win32u is
not used. FreeType renders the fonts in the Windows font directory.

Luna 6 ran the frozen candidate in a throwaway VM from the Civ3 layer image.
The primary audited the raw JSON: actual arguments, sessions, exact markers
and numeric exits. Every Wine row also has WINE_LOAD_APPLICATION
status=00000000 and GUEST_EXIT code=0 ... HOST_RETURNED.

The native session-0 cursor failure is the Windows rule that SetCursorPos
needs an interactive window station (ERROR_REQUIRES_INTERACTIVE_WINDOWSTATION).
The Wine rows are headless and pass in both sessions. Wine and native lines
match exactly except focus, where native reports more WM_SETFOCUS/
WM_KILLFOCUS messages (6/5 or 6/6) than Wine (3/3); the control requires at
least two and one.

Regressions on the same candidate: the focused suite (35 fixture children),
cross (29) and unmodified (16) complete with no failures, crashes or
timeouts. The exception suite (8) last passed on d9f3498, which already
contained the GUI stack.

Fixes found by earlier rounds of this control set:
- d9f3498: every process after the first asserted in sysparams.c. The native
  registry opens a link key itself only for OBJ_OPENLINK, not Wine's
  REG_OPTION_OPEN_LINK create option (fixed in 54861b5).
- 54861b5: GetCursorPos returned 0,0. Without explorer.exe /desktop the
  desktop window stayed 0x0 and the server's cursor clip empty (fixed in
  c56a5df, from X11DRV_SetDesktopWindow and explorer's ClipCursor(NULL)).
