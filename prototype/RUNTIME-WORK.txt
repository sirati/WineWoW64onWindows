Wine 11 WoW64 on native Windows, runtime integration

Scope: socket-backed DLLs, APCs, IOCP/cancellation/callbacks, pending event
and eventless I/O, guest threads/contexts, XSTATE, guarded stacks and
mitigation compatibility. The Civ3 target also includes Wine's own headless
GUI path: win32u, wow64win, wineserver window/message state and nulldrv.
ARM64, sound output and additional NT services are excluded.
Linux MinGW-w64 cross-builds the implementation. Luna 6 executes VM tests
and may create test helpers; it does not change implementation files.

Architecture retained

Wine loads the guest application and its normal DLLs. Original Wine PE
ntdll/kernelbase/kernel32/msvcrt, loader indexes, TLS/FLS lifecycle, SEH/C++
handlers, wow64 argument conversion, ws2_32 frontend, DNS/ancillary marshalling,
APC dispatcher and IOSB publication remain in use. Native Windows adapters
replace host storage, AFD/file operations and thread identities. No Linux
file I/O backend or native Windows WoW64 EXE loader is used for the guest.
Native x64 unixlib DLLs use Wine's builtin search and cache layout; the Civ3
renderer is loaded from `x86_64-native`.
The bootstrap uses private COFF symbols from a pinned Wine 11 PE build.

Native plus 10 Wine repeated-overflow controls pass. Native plus five Wine
AVX, stack-growth and expanded mitigation controls pass. Full regression is
complete on this candidate, with zero required failures.

This candidate adds Wine's memory-protection notification hook for CRT stack
overflow reset. Wine _resetstkoflw guards its own active stack page. Windows
can consume that guard while copying native protection-call outputs, without
entering the guest stack handler. The hook runs Wine grow_thread_stack for
that active page before the Wine thunk copies its remaining outputs back.
Normal guard faults use the same original Wine routine and per-stack registry.

The protection test now checks loaded bootstrap DLLs and the syscall gate,
as well as the application image, NX execution and read-only writes.

Mitigation boundaries

The host/native DLL advertise DYNAMIC_BASE, HIGH_ENTROPY_VA and NX_COMPAT.
DEP reporting uses the full structure, including its permanent flag.
Forced ASLR and CFG launch policies run on the VM. The CFG result does not
establish CFG instrumentation/enforcement for the Wine-loaded guest.
Dynamic-code prohibition rejects the gate's RW-to-RX transition with Windows
error 1655. CET-enabled and CET-strict launch both exit with c0000409 at host RVA 0x1194,
the Wine IRETQ compatibility-mode restore. Exception info0 is hex 0x39,
decimal 57, FAST_FAIL_CONTROL_INVALID_RETURN_ADDRESS. Raw policy logs and
independent host disassembly are under evidence/final-runtime.
These results describe the historical private bootstrap/transition mappings.
No policy is disabled by the test launcher or the runtime.

Build notes

Wine winebuild emits its own export table. --exclude-all-symbols and
--no-gc-sections keep MinGW auto-export generation from replacing that table.
check-pe-exports.py verifies all 134 original ws2_32 names, ordinals and
forwarders. GNU delay-import libraries plus Wine winecrt0 delay_load preserve
lazy imports for dnsapi/iphlpapi/user32/advapi32.

The filesystem-base recovery test deliberately clears guest FS and is Wine-
only. Running it as a native Windows application is expected to crash because
there is no host recovery handler in that mode.

README.txt records compatibility. REMAINING-WORK.txt records unresolved
items and estimated difficulty. Commit history retains prior diagnostics.

CET continuation diagnostic

The standalone Nix continuation-diagnostic output tests Windows NtContinue
with a native CONTEXT requesting CS=0x23. Its first VEH runs on the saved
native stack, as the port does. Windows 11 build 26100 reports CS=0x33 at
the trap, so this did not enter compatibility mode. A successful trap at
the expected IP alone would have been insufficient evidence. This diagnostic
has no runtime dependency and does not replace Wine's transition code.
